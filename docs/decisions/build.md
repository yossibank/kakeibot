# 作り方

> [!NOTE]
> 開発の道具と運用、画面に出す言葉をどう決めたかと、その理由が分かる。

## 共通化

**決定：Swift で先に作り、fixtures で Kotlin 版とそろえる。**

| 項目 | 内容 |
| --- | --- |
| 理由 | Swift が得意で iPhone を毎日使い、AI の段階は Swift 専用である。iOS をストアに出してから、13 番で Android に取りかかる |
| 却下 | Kotlin Multiplatform、Compose Multiplatform、Flutter、Swift SDK for Android |

## Android の範囲

**決定：最初のリリースは、無料の機能だけで出す。**

| 項目 | 内容 |
| --- | --- |
| 理由 | 同期と共有は iCloud なので Android に無い。Pro の中身を決める前に、1〜9 の画面をそろえられる |
| 却下 | 最初から Google Play の課金で Pro を入れる、Pro を設けず全部を無料にする |

> [!IMPORTANT]
> - テーマを作る・字体など、iOS で Pro の機能は、最初は出さない。
> - レシートの読み取りは入れない。iOS は Apple の Foundation Models で品目を読むためである。

## Android のアイコンの絵

**決定：アイコンの絵柄（`Icon.Glyph`）は、Material Symbols の絵で出す。**

| 項目 | 内容 |
| --- | --- |
| 理由 | SF Symbols は Apple の端末の外で使えない。Material Symbols は Apache 2.0 で、アプリに入れて配れる |
| 却下 | 絵を自分で描く、絵柄をやめて絵文字だけにする |

> [!IMPORTANT]
> - Outlined の太さ 300 を使う。iOS の細い線の絵に近い。
> - 同じ物の絵が無い絵柄は、近い意味の絵を当てる。iOS と絵が違っても、絵柄の名前と色は同じにする。

## Android のモジュール

**決定：iOS のターゲットに合わせて分ける。**

| 項目 | 内容 |
| --- | --- |
| 理由 | Core を Kotlin に移すとき、iOS のどこに当たるかを追いやすい。`:core` は Android に頼らず、速くテストできる |
| 却下 | 1 つのモジュールにまとめる |

### Store のモジュール

**決定：`:store` は Kotlin Multiplatform にし、JVM と Android を対象にする。**

| 項目 | 内容 |
| --- | --- |
| 理由 | Room は、JVM 版と Android 版で DB を開く入口が違う。JVM のターゲットを残すと、テストは端末なしで速く走る |
| 却下 | JVM だけのモジュール、Android のライブラリにして Robolectric でテストする |

> [!IMPORTANT]
> JVM だけのモジュールは、アプリの実行時に Room の Android 版が選ばれ、DB を開く所で落ちる。エミュレーターで確かめた。

### アプリのモデルのテスト

**決定：画面のモデルは、`:app` の JVM のテストで確かめる。**

| 項目 | 内容 |
| --- | --- |
| 理由 | Room の Android 版は、空の `Context` でメモリに開ける。SQLite は JVM 版の部品を Gradle が渡す |
| 却下 | Robolectric、モデルを JVM のモジュールに移す |

> [!NOTE]
> テストには、本物と同じ形の `android.database.SQLException` を置く。テスト用の空の型では、保存がまれに失敗した。

## リポジトリ

**決定：1 つにまとめる。**

| 項目 | 内容 |
| --- | --- |
| 理由 | fixtures と書き出しの形式を両 OS で共有する |
| 却下 | OS ごとに分ける |

## 対応端末

**決定：iPhone と iPad。**

| 項目 | 内容 |
| --- | --- |
| 理由 | 広い画面で、記録の一覧と振り返りを並べて見られる。Mac で動かす土台にもなる |
| 却下 | iPhone のみ。画面の配置とスクリーンショットは減るが、iPad では拡大表示になる |

> [!IMPORTANT]
> - iPhone は縦向きだけ、iPad は縦と横に対応する。
> - 文言の「iPhone」は、動かしている端末の名前に置き換える。相手やほかの端末は「端末」と書く。
> - シートは、iPad では幅 580 pt・高さ 800 pt の窓で出す。入力シートが切れずに収まる大きさである。
> - 高さを中身に合わせるシートは、iPad では窓の高さを中身に合わせる。
> - キーボードをつないでいる時は、テンキーを数字・`+` `-` `*` `/`・Return・Delete で打てる。
> - 最初の設定は、中身を幅 580 pt までにして中央に置く。
> - 入力シートは、窓の高さが足りない時だけ縦にスクロールする。

| 項目 | 内容 |
| --- | --- |

| 却下 | XcodeGen、Tuist |

## ワークスペース

**決定：プロジェクトと 2 つのパッケージを、`.xcworkspace` で並べる。**

| 項目 | 内容 |
| --- | --- |
| 理由 | ナビゲーターでプロジェクトとパッケージが同じ高さに並び、見分けやすい |
| 却下 | パッケージのフォルダをプロジェクトの中に入れる |

## 整形

**決定：Swift は SwiftFormat（Mint で版を固定）、JSON は jq（版は固定しない）で整形する。**

| 項目 | 内容 |
| --- | --- |
| 理由 | 自分で整形を走らせずに済む。一部だけステージしたファイルは、pre-commit が整形を取り消すので壊れない |
| 理由 | JSON は jq の標準の形にそろえると、整形の道具を自作せずに済む |
| 却下 | hook は違反を止めるだけで直さない、hook がステージし直して commit まで通す |
| 却下 | SwiftLint も入れる |
| 却下 | JSON の短いものやケースを 1 行に畳む。整形の道具を自作することになる |

> [!IMPORTANT]
> commit の前に pre-commit が整形し、直したら commit を止める。ステージし直すのは人。

## 文書の確認

**決定：文書の書き方の決まりは、Claude Code のフックと `make verify-docs` で確かめる。**

| 項目 | 内容 |
| --- | --- |
| 理由 | 文書を書くのはほぼ Claude なので、フックで書いたその場で直せる。フックが見ない文書は `make verify-docs` で見る |
| 却下 | pre-commit で確かめる、自動では確かめない |
| 理由 | 文書を書くのはほぼ Claude なので、書いたその場で直せる。フックが見ない文書は `make verify-docs` で見る |

> [!IMPORTANT]
> 文書と実物の一致は、`scripts/docs-check.py` で確かめる。見るものは [architecture のリポジトリ](../architecture.md#-リポジトリ)にある。文書だけの PR では、`make verify-docs` で走らせる。

## テストの走らせ方

**決定：CI は置かない。**

| 項目 | 内容 |
| --- | --- |
| 理由 | リポジトリは非公開で、GitHub Actions を使わない |
| 理由 | 結果の変わらない変更で待たず、同じビルドを 2 回せず、長いログから失敗を探さずに済む |
| 却下 | GitHub Actions で走らせる、手元の Mac を GitHub Actions のランナーにする |
| 却下 | push のたびに走らせる、`make test-build` も別に走らせる、xcodebuild の出力をそのまま出す |
| 却下 | 先にシミュレーターを起動する。起動の途中は `simctl list` と `xcodebuild` が待たされ、かえって遅い |

> [!IMPORTANT]
> - PR を作る前に、Claude が手元で `make test` を 1 回走らせ、結果を PR の本文に書く。
> - push し直すときは、Swift か fixtures を変えたときだけ走らせ直す。
> - 文書だけの PR では走らせない。
> - ビルドは別に走らせず、`make test` のビルドで兼ねる。
> - ビルドとテストの出力は xcbeautify で整える。
> - 画面のモデルのテスト（FeaturesTests・AppFeatureTests）は、テストプランで並行させない。
> - 並行させると、メインの処理の順番待ちで、変化を待つ時間が全体の長さまで延びるため。

| 項目 | 内容 |
| --- | --- |
| 理由 | 日本語で使う人に向けたアプリで、日付選択などの OS の部品も日本語で出る |
| 却下 | 英語で書いて日本語に訳す |

## 画面の言葉づかい

**決定：説明と知らせは「記録しました」「動かせます」のように、柔らかい丁寧な言い方で書く。**

| 項目 | 内容 |
| --- | --- |
| 理由 | 使ってもらうアプリなので、言い切りより柔らかく聞こえる |
| 却下 | 「記録した」のような言い切り |

> [!IMPORTANT]
> ボタンは「取り消す」「削除」のように短く書く。
