# 決めたこと

今有効な決定だけを書く。決定を変えたら、その項目を書き換える。

## 作り方

リポジトリ全体と、作業の道具の決定。

### 共通化

Swift で先に作り、fixtures で Kotlin 版とそろえる。

| 理由 | 選ばなかった案 |
| --- | --- |
| Swift が得意で iPhone を毎日使う。Android に取りかかるのは 6 番。AI の段階は Swift 専用 | Kotlin Multiplatform、Compose Multiplatform、Flutter、Swift SDK for Android |

### リポジトリ

1 つにまとめる。

| 理由 | 選ばなかった案 |
| --- | --- |
| fixtures と書き出しの形式を両 OS で共有する | OS ごとに分ける |

### 対応端末

iPhone のみ。

| 理由 | 選ばなかった案 |
| --- | --- |
| iPad 向けの画面の配置とスクリーンショットが要らない。あとから足せる | iPhone と iPad |

### 署名

自動。

| 理由 | 選ばなかった案 |
| --- | --- |
| 1 人・端末 1 台・CI なしなので、端末の追加・更新・提出を Xcode に任せられる | 手動 |

### プロジェクトのファイル

`.xcodeproj` をそのまま管理する。

| 理由 | 選ばなかった案 |
| --- | --- |
| 1 人なので衝突しない。中身はほぼパッケージ側 | XcodeGen、Tuist |

### 整形

SwiftFormat（Mint で版を固定）。commit の前に pre-commit が整形し、直したら commit を止める。ステージし直すのは人。

| 理由 | 選ばなかった案 |
| --- | --- |
| 自分で整形を走らせずに済む。一部だけステージしたファイルは、pre-commit が整形を取り消すので壊れない | hook は違反を止めるだけで直さない、hook がステージし直して commit まで通す、SwiftLint も入れる |

### 文書の確認

Claude Code のフック（claude-config の `hooks/check-docs.py`）で、書き方の決まりを確かめる。

| 理由 | 選ばなかった案 |
| --- | --- |
| 文書を書くのはほぼ Claude なので、書いたその場で直せる。リポジトリごとの準備が要らない | pre-commit で確かめる、自動では確かめない |

## iOS の構成

iOS のパッケージ、画面、DB の決定。

### パッケージ

KakeibotKit（iOS・macOS）と KakeibotApp（iOS 専用）の 2 つ。

| 理由 | 選ばなかった案 |
| --- | --- |
| 1 つにすると、iOS 専用のターゲットのせいで Core の `swift test` が失敗する。`--filter` で絞っても全ターゲットがビルドされる（Swift 6.4 で確認済み） | 1 つのパッケージにターゲットを分けて入れる |

### 画面の作り

SwiftUI ＋ `@Observable`、処理のある画面だけモデル。

| 理由 | 選ばなかった案 |
| --- | --- |
| 計算は Core にあり、テストもされる | TCA、全画面に ViewModel |

### Features

1 つのターゲット、画面ごとのフォルダ。

| 理由 | 選ばなかった案 |
| --- | --- |
| 1 人では、ターゲットを分ける管理の手間が勝つ | 機能ごとにターゲットを分ける |

### 部品の置き場所

値を表示するだけの部品は DesignSystem、データを読み書きするものは Features。

| 理由 | 選ばなかった案 |
| --- | --- |
| 部品の置き場所を 1 つにする | Features の中に Shared/ を置く |

### 依存を渡す方法

モデルを作るときに引数で渡す。Environment で渡すのはテーマだけ。

| 理由 | 選ばなかった案 |
| --- | --- |
| `@State` でモデルを作る時点で Environment を読めない | Environment、部品をまとめた型 |

### DB

GRDB の DatabasePool を App Group に置く。

| 理由 | 選ばなかった案 |
| --- | --- |
| SQL で集計と移行を書ける。ウィジェットからも読める | SwiftData、SQLDelight |

### DB の変更を画面に届ける

`ValueObservation`。

| 理由 | 選ばなかった案 |
| --- | --- |
| 依存を増やさない | GRDBQuery、SQLiteData |

### 書き出しの形式

Core に置く。

| 理由 | 選ばなかった案 |
| --- | --- |
| DB なしで往復を試せる。Android に移せる | Store に置く |

### 通知

予約されているべき通知は Core で計算し、Notifications は差だけを OS に反映する。

| 理由 | 選ばなかった案 |
| --- | --- |
| fixtures で試せる | Notifications が DB を読む |

### 入力の入口

どこからでも開けるシート。

| 理由 | 選ばなかった案 |
| --- | --- |
| 1 手で記録できる | 入力用のタブ |

## データ

保存するデータの持ち方の決定。

### 財布の種類

現金・銀行・カード・電子マネー・ポイント。

| 理由 | 選ばなかった案 |
| --- | --- |
| カードの引き落としを銀行からの振替で記録する | 銀行なし |

### 期間の呼び方

期間の終わりが入っている月。

| 理由 | 選ばなかった案 |
| --- | --- |
| 1 日始まりでも給料日始まりでも同じ決まりで済む | 期間の始まりの月 |

### 月末を超える月の始まり

その月の最終日から始める。

| 理由 | 選ばなかった案 |
| --- | --- |
| 固定費の日付と同じ決まりで済む。期間が途切れず、重ならない | 翌月の 1 日から始める、29 日以降を選ばせない |

### 支出なしの日

印を作る（`no_spend_day`）。

| 理由 | 選ばなかった案 |
| --- | --- |
| 印がないと、支出のない日にも記録忘れの通知が来る | 作らない |

### 予算の履歴

「この月から」の行を足す。

| 理由 | 選ばなかった案 |
| --- | --- |
| 額を変えても過去の月が変わらない。月替わりの写し作業が要らない | 月ごとに全カテゴリを写す、履歴なし |

### よく使う組み合わせ

記録から自動で出す。

| 理由 | 選ばなかった案 |
| --- | --- |
| 表が要らない | 自分で固定する |
